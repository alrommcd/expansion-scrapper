**Diagnostic phase (closed)**: extensively tested whether direct NRI/absentee signals (POA text, "owner abroad" phrasing, phone/country-code prefixes) are recoverable from MagicBricks sale listings, rental listings, and detail pages. Verdict: no - real listing text at ~1% ceiling for any direct signal, confirmed across sales, rentals, and detail-page full text. Also checked whether a public bridge exists from a listing's address to a government property record (IGR Maharashtra, MahaRERA, PMC, PCMC) - no: every public portal requires a government-issued property/survey/CTS/document identifier that no listing site exposes. Full findings in DECISIONS.md (2026-07-05 through 2026-07-06 entries). Conclusion: proxy signals from listings (staleness, multi-property ownership, never-occupied language) are the honest ceiling for this data source; true identity resolution needs registry data HouseEazy would have to source separately, not public self-service scraping.

Known issues / caveats that matter for how these assets should be used:
- **Asset 1's signals are proxies, not confirmed identity.** Multi-property-owner is restricted to distinctive (2+ word) names to avoid common-first-name collisions - even so, it's a name-matching heuristic, not a verified same-person match. Never-occupied uses a refined 4-keyword rule (dropped "brand new" after it proved to be 100% false-positive-prone in manual review). Staleness (90d+) is supporting context only, not a qualifying signal.
- **Hyderabad's raw candidate count was initially inflated 2x by a scraper gap, found and fixed before shipping**: its MagicBricks card layout never exposes a `data-summary='society'` element (unlike every other city), so all 1050 scraped listings initially had a null society name, which silently broke cross-corridor dedup for that city alone (signature-based matching requires a society name) and let the same physical listing get double-counted as two properties under one owner. Confirmed via a first-run anomaly check (103/1050 flagged, a 10x outlier against every other city's rate) rather than shipped as-is. Fixed by adding a URL-slug-based society-name fallback to `scraper/magicbricks.py` and backfilling Hyderabad's existing rows from their stored `detail_url`, dropping the count to 52 at that point.
- **A user audit of the 114-row shipped output caught two more real bugs the Hyderabad fix didn't cover**, corrected to the final 108: (1) Bangalore was *also* 100% blank society (same root cause, just not re-checked on cities scraped before the fix existed) - fixed by running the same backfill uniformly across all 5 cities instead of assuming it was Hyderabad-only. (2) "Owner: Magicbricks User" / "Owner: MB User" are the site's own placeholder text for a name it failed to capture, not real people - confirmed via 5 occurrences spanning 4 different cities with unrelated societies/prices - but as two-word strings they passed the distinctiveness filter and were grouped as repeat owners; now excluded by exact match. (3) The dedup signature's carpet-area fallback only bridged two listings that both lacked an area value - it never bridged one with a real area against one without, missing a confirmed Bangalore duplicate (same price/owner/near-identical text/same URL) purely because one side had a parsed area and the other didn't; fixed by dropping area from the signature key entirely (dedup now keys on society+price only, with the same description/owner-match confirmation gate as before). Full trace, including which remaining matches are well-corroborated vs. carry disclosed name-collision risk, in DECISIONS.md (2026-07-06).
- Residual, pre-existing and not fixable by code: some rows still show a blank society because their listing never had a capturable `detail_url` at scrape time (a separate, already-known ~15-20% href-capture gap). A handful of remaining Signal 1 matches rely on a MagicBricks *project-level* detail URL rather than a unit-level one, which makes the owner_note "who's on this page" check weak evidence for those specific rows (a big project's shared page lists many unrelated sellers) - this affects confirmability, not the underlying owner-name-based grouping logic.
- **Registry lookups (IGR/MahaRERA/PMC/PCMC) do not work from listing data** - confirmed structurally blocked, not just difficult.
